# ADR-0011: Use `clock_timestamp()`, Not `now()`, for `created_at`/`updated_at`

## Status
Accepted

## Context
`docs/adr/0002-postgresql.md` established Postgres as the primary
database; `app/infrastructure/db/mixins.py` (Milestone 2) used
`server_default=func.now()` for `created_at`/`updated_at`, reasoning that
a database-side default avoids clock-skew between application servers.

That reasoning was correct, but the specific function wasn't: Postgres's
`now()` returns the *transaction's* start time, which is identical for
every statement executed within the same transaction. Milestone 3's job
ingestion — which can insert many `Job` rows in a single request/
transaction — surfaced this directly: an integration test asserting
newest-first pagination order failed because all rows in a batch received
the exact same `created_at`, leaving their relative order to depend on
whatever the query's secondary sort key happened to break ties with.

## Decision
Use `func.clock_timestamp()` instead of `func.now()` as the
`server_default` (and `onupdate`, for `updated_at`) on `CreatedAtMixin`
and `TimestampMixin`. `clock_timestamp()` returns the actual wall-clock
time at each statement's execution, giving every row within a batch a
distinct, correctly-ordered timestamp.

## Alternatives Considered
- **Set `created_at` in Python at insert time** (`datetime.now(timezone.utc)`)
  instead of a database-side default — sidesteps the issue entirely, but
  reintroduces the clock-skew-between-app-servers problem the original
  server-side-default decision (Milestone 2) was made to avoid, and
  reverses that reasoning for no real benefit now that a same-effect,
  database-side fix exists.
- **Keep `now()` and break ties on `id` alone** — already how
  `list_jobs()`'s `ORDER BY created_at DESC, id DESC` works as a tiebreaker,
  but a UUIDv4 secondary sort key is not chronological, so "ties broken by
  id" would silently produce an arbitrary, not merely coarse-grained,
  order — not an acceptable trade for a "newest first" guarantee.

## Consequences
- Migration `4f9e6c86a995` alters the `server_default`/`onupdate` on every
  `created_at`/`updated_at` column across all six tables. It's a
  hand-written migration, not autogenerated — Alembic's `--autogenerate`
  does not reliably diff server-side default *expressions*, a limitation
  worth flagging for future migrations that change a default's SQL
  expression rather than adding/removing a column.
- `clock_timestamp()` is *not* transaction-safe in the sense `now()` is
  (two reads of `clock_timestamp()` in the same transaction can differ) —
  the correct behavior here, since `created_at` should reflect the actual
  moment a row was written, not a value shared across an entire
  transaction's other statements.
